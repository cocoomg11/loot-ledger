# CLAUDE.md: Loot Ledger

Foundry VTT module (v14, dnd5e) that copies the classic MMO item compendium from the `wow-classic-items` module into world compendiums with sell-accurate prices, and generates rollable loot tables (by quality x level band, item type, mixed drops, creature type). Optionally converts items to 5e. Code only, no item data. Requires `wow-classic-items`. Public repo, MIT.

## File map (`scripts/`)
- `main.mjs` entry: settings (`coinRatio`, `convertOnBuild`, `reviewBoard`, `qualityColours`, `qualityRarityFallback`, `qualityPicker`, plus the client `itemTooltip` via `tooltip.mjs`), the "Build loot pools" settings menu (with a Review board button), feature registration, API registration.
- `data.mjs` pure constants and helpers: qualities, level bands, categories, creature regexes, item parsing, prices, coin formatting.
- `build.mjs` build pipeline: copies source items into world pack "Loot Ledger · Items" (price = 2x vendor sell, so selling pays the original amount), then writes "Loot Ledger · Tables".
- `convert.mjs` converter classic MMO item -> dnd5e 2024 item. Every feature must trace to one source tooltip line; untranslatable lines go to GM review, never invented.
- `api.mjs` public API: `game.modules.get("loot-ledger").api` (build, convertToPack, reviewBoard, setQuality, qualityOf, ...).
- `review-model.mjs` (pure) review statuses, actions, rebuild protection (`protectReviewed`, `carryReview`), table exclusion (`isRejected`), queue filters / counts, `itemView`, shortcuts; `review.mjs` the Review board window (ApplicationV2) and its Build Report button.
- `quality-model.mjs` (pure) the quality normaliser over core's `quality()` (aliases, heirloom, no rarity; see Key patterns), resolution (explicit flag, then rarity fallback), `qualityClass` / `syncTheme`, flag update; `quality.mjs` render hooks, item sheet picker, "Set quality" context entry, Item Piles observer, `setQuality`.
- `suffix.mjs` pure random-suffix logic (group, power, weighted pick, effects, naming, price, item update, report page); `suffix-hooks.mjs` its settings (`randomSuffixes`, `suffixMode`), the active-GM `createItem` hook, the item context-menu entry, `api.rollSuffix` / `api.suffixes`.
- `events.mjs` (pure payload + bail-outs, `loot-ledger.itemDropped`) and `cleanup.mjs` (pure `cleanupPlan`, GM `api.removeData`).
- `tooltip.mjs` opt-in item tooltip (client setting `itemTooltip`, default off, shown only while Shift is held): document-level pointer/key listeners, item lookup from `data-item-uuid` / `data-uuid` / `data-item-id` / `.directory-item[data-entry-id]` and chat cards (`getAssociatedItem`) and Item Piles rows (`item-piles-model.mjs`; hooks registered only while the tooltip is on), one fixed `#loot-ledger-tooltip` element carrying core's `UI_CLASSES`. Read-only.
- `tooltip-data.mjs` pure tooltip model + HTML render (flag via the quality normaliser, else rarity tier → core quality key `qualityOf`, stats, excerpt, price via core `formatCoins` with the `coinRatio` setting, slot compare); tested in `tests/tooltip-data.test.mjs`.
- `item-piles-model.mjs` (0.2.2, pure) Item Piles rows → items: `ITEM_PILES_HOOKS` (Item Piles' documented `item-piles-render*Item` / `-mouseHover*Item` hooks pass `(element, item)`), `rowMap()` (WeakMap element → item, filled by those hooks while the tooltip is on), fallback `matchRowItem(actor.items, { name, img })` (name+img → name → img, single match only) on `pileActorOf(app)` (`app.actor`, merchant `app.merchant`). Checked against Item Piles 3.3.4 source; tested in `tests/item-piles.test.mjs`.
- `vendor/wanderers-core/` **wanderers-core 0.5.0** (0.2.2), pinned by `wanderers-core.lock.json`; never edit by hand: `node vendor/wanderers-core/vendor.mjs update X.Y.Z` (behind the agent proxy: `NODE_USE_ENV_PROXY=1 NODE_EXTRA_CA_CERTS=/root/.ccr/ca-bundle.crt`). Core's CONVENTIONS.md applies. Used so far: `quality`/`QUALITY_KEYS`, `formatCoins`, `UI_CLASSES` (tooltip root, so `--wc-q-*` tokens apply), the shared stylesheet (first in `module.json` `styles`). Never write the revision class (`wc-r3`) out; a test checks.
- Also `styles/`, `lang/en.json`.

## Key patterns
- Conversion: `api.convertToPack`, and on this branch Build converts when `convertOnBuild` is on (off by default).
- Stat-less items reflavour an official item of the same slot/rarity, copied at build time from the user's installed compendiums; the repo stores names only, never official text.
- Prices are stored as decimals in the largest coin; the 5e converter never raises ability scores.
- No feature registry, health check or update-notes card; settings are minimal.
- `build({ dryRun: true })` runs every stage up to the writes and returns `{ dryRun, plan, report, build (counts), ... }`. Every write path (`applySync`, `clearPack`, folder and table creation, `writeReport`, chat, pack creation, confirm dialog) is skipped and also guarded by `noWrites(dryRun, ...)`, which throws. Any new write in `build()` must be skipped under `dryRun` and guarded the same way; `tests/build.test.mjs` spies on every write call and asserts zero.
- **Review decisions** live on the converted item: `flags.loot-ledger.review = {status, note, by, at}` (status pending | accepted | tweaked | skipped | rejected). In `build()`, `protectReviewed` drops accepted/tweaked ids from the converted plan's `replace` unless `force` (removals from the source still happen); `carryReview` copies the review onto rewritten items (force resets accepted/tweaked to pending with `previous`). Rejected ids (read from the converted pack even when conversion is off) are made non-rollable before `planTables`. Keep all three when changing the build.
- **Quality colours: one system.** Colours are core's `--wc-q-*` tokens only (vendored stylesheet); `scripts/quality-model.mjs` is the LL normaliser over core's `QUALITIES` / `quality()` (colour-word aliases, extra `heirloom` tier, below common (no rarity, "", "mundane", "none") = `poor` grey for physical item types when `qualityRarityFallback` is on; null = no colour for unknown / homebrew values (core would say common), non-physical types without rarity, and empty / "none" / "auto" flags, which mean "not set"). Mark a coloured element with `qualityClass(key)` (adds `ll-q ll-q-<key>` plus core's `UI_CLASSES`, so the tokens resolve on the element) and call `syncTheme(el)` after inserting it (copies a window's own `theme-*`; the body theme is left to core). Never hand-write `ll-q` classes, hex colours or the revision class; tests check. The only module colour token is `--wc-q-heirloom` (core pattern, core 0.5.2 ships it (pushed, unpublished): once published run `NODE_USE_ENV_PROXY=1 NODE_EXTRA_CA_CERTS=/root/.ccr/ca-bundle.crt node vendor/wanderers-core/vendor.mjs update 0.5.2`, drop it from `styles/loot-ledger.css`, and empty `EXTRA_QUALITIES` (core's `QUALITIES` then includes heirloom; don't list it twice)). The tooltip's `qualityOf` uses the same normaliser, falling back to core's `quality()` (always a colour).
- **Quality colours** are render-hook only (no per-frame work, no document writes except the GM picker / `setQuality`). Explicit `flags.loot-ledger.quality` (same key Build writes) beats the rarity fallback. Item Piles windows are Svelte: one MutationObserver per open window (hooks `item-piles-openInterface` / `-closeInterface`), matched by item name.
- Settings `reviewBoard`, `qualityColours`, `qualityPicker` need a reload and register nothing when off; `qualityRarityFallback` is live.
- "<Random enchantment>" is not added to the not-converted list; the converter sets `flags.loot-ledger.randomSuffix` + `suffixGroup` instead. Suffixes roll on drop (never at build): active GM only, only when conversion AND `randomSuffixes` are on (no hooks registered otherwise), and never twice (`flags.loot-ledger.suffix`); rerolls start from `suffix.base`. Numbers live in rules.mjs section 9; stat suffixes reuse `STAT_PASSIVE`.
- Writes (build, conversion) run from a GM-triggered action; do not add automatic hooks that write documents without an active-GM check.

## Focus tagging (research)
Researched 2026-11-01 against dnd5e 6.1.0 (branch `6.1.x`, commit `0a247dd`, read-only; no code written). Permalinks are pinned to that commit (`https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/` = `https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/`).

- **Yes, there is a Focus item property.** It is the item property key `foc` ("Focus"), declared in `CONFIG.DND5E.itemProperties` ([`module/config.mjs` L1960-L1962](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/module/config.mjs#L1960-L1962)); label `DND5E.ITEM.Property.Focus` = "Focus" ([`lang/en.json` L3913](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/lang/en.json#L3913)).
- **Storage:** a plain string in the item's `system.properties` Set (`SetField(StringField)`), so an item is a focus when `item.system.properties.has("foc")`. There is no separate boolean or system field. Source data stores it as an array: `system.properties: ["foc"]` (e.g. [SRD Staff, `staff.yml` L79-L81](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/packs/_source/equipment24/adventuring-gear/spellcasting-focuses/arcane-focus/staff.yml#L79-L81), `["foc","ver"]`, a weapon-type staff; [`wand-of-web.yml` L58-L60](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/packs/_source/items/wand/wand-of-web.yml#L58-L60), `["foc","mgc"]`, equipment subtype `wand`). Schemas: [`equipment.mjs` L64](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/module/data/item/equipment.mjs#L64), [`weapon.mjs` L71](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/module/data/item/weapon.mjs#L71), [`tool.mjs` L59](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/module/data/item/tool.mjs#L59).
- **Item types that may carry it** (`CONFIG.DND5E.validProperties`, [`module/config.mjs` L2051-L2106](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/module/config.mjs#L2051-L2106)): **equipment** (L2063-L2068), **weapon** (L2076-L2094) and **tool** (L2102-L2105). Not valid for **loot** (L2073, only `mgc`), consumable (L2055, `mgc`), container (L2058), feat, spell or class. `validProperties` is applied by the sheet and the compendium browser filter ([`item-description.mjs` L38-L43](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/module/data/item/templates/item-description.mjs#L38-L43), [L95](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/module/data/item/templates/item-description.mjs#L95)); the data field itself is an unrestricted string set, so a script could store `foc` on a loot item, but the sheet would not show it and dnd5e does not support it (inference from the code, not tested). Ammo consumables gain only properties flagged `isPhysical` ([`consumable.mjs` L176-L185](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/module/data/item/consumable.mjs#L176-L185)); `foc` is not one.
- **No mechanics are driven by it.** Nothing in the system code reads `foc` other than config and the property filter (no spell component or casting check uses it); it is a tag shown on the item and filterable in the compendium browser. Equipment subtype does not matter (valid for any `equipment` type, `trinket` included).
- **Separate from the property:** `CONFIG.DND5E.focusTypes` (arcane / druidic / holy, each mapping to SRD 5.2 item UUIDs; [`module/config.mjs` L1825-L1853](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/module/config.mjs#L1825-L1853)) is only used by the starting-equipment "focus" choice ([`starting-equipment.mjs` L148-L151](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/module/data/item/templates/starting-equipment.mjs#L148-L151)). dnd5e's own SRD focus items are inconsistent: the Staff carries `foc`, but Crystal, Sprig of Mistletoe and Amulet are equipment type `trinket` with `properties: []` (e.g. [`crystal.yml` L47](https://github.com/foundryvtt/dnd5e/blob/0a247dd7d88d4646930ac140d73363282d25b24e/packs/_source/equipment24/adventuring-gear/spellcasting-focuses/arcane-focus/crystal.yml#L47)). In dnd5e's `items` pack source, 43 items have `foc`: 30 equipment (wands, rods and similar) and 13 weapons (staffs).
- **Implication for Loot Ledger:** to tag a converted item as a focus, add `"foc"` to `system.properties` on `equipment`, `weapon` or `tool` items only. Items that become `loot` cannot carry it, so a focus-like item (wand, staff, orb) must be converted to equipment/weapon, not loot. Do not store it as a flag.

## House practices
- **Releases:** the tag is `vMAJOR.MINOR.PATCH` (the Release workflow fails otherwise; `tests/house.test.mjs` checks the regex). Agents never tag or publish. Every release ends with a live checklist (what only a live world can confirm) in the handoff.
- **Compatibility:** `module.json` `compatibility` minimum/verified 14; dnd5e under `relationships.systems` with a minimum and `verified`. Optional integrations (Item Piles, Wayfarer's Toolkit) go under `recommends`, never `requires`. The source item module is the data source and stays `requires`.
- **Hot hooks:** hooks on frequent events (`createItem`, `updateItem`, `renderChatMessageHTML`, render hooks) must return on the cheapest irrelevant check first, before any lookup or DOM work. Register nothing when the feature's setting is off.
- **Settings size:** world settings stay small (booleans, short strings). Never store a growing list or record in a setting; use compendium or document flags. Add every new setting key to `SETTING_KEYS` in `cleanup.mjs` (a test enforces it).
- **Namespace:** all flags under `flags.loot-ledger.*`. Talk to other modules only through their API or hooks, never their internals; expose ours through `api` and documented hooks.
- **Data versions:** converted items carry `flags.loot-ledger.converted.version` (= `CONVERTER_VERSION`); the hash covers `CONVERTER_VERSION`, `COPY_VERSION` and the rules. Bump `CONVERTER_VERSION` / `COPY_VERSION` whenever output changes; a bump rewrites unreviewed items on the next Build but `protectReviewed` keeps accepted / tweaked ones unless `force`. Keep that test green.
- **Cleanup:** anything the module writes into a world must be removable. Update `cleanup.mjs` and the README "Where Loot Ledger keeps its data" list when adding a new write location.
- **API docs:** the README "Public API and hooks" table lists every API member and hook, marked stable or experimental. Update it in the same commit as the change. New hooks start experimental.
